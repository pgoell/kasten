# Save path orderings: presses on a todo row

Part of [save path orderings](/reference/save-path-orderings.md). The columns are explained in [How to read the table](/reference/save-path-orderings.md#how-to-read-the-table). Rows keep their numbers on every page, so "As 82" points to the same row wherever it sits.

## Orderings

| # | Ordering | Must hold | Loses typed text if wrong | Test |
|---|---|---|---|---|
| 124 | A card dropped on another column, or a state key, whose write the store refuses. | The press draws the new state on the row at once, and the list is read again once the last press settles, so the card goes back to where the store has it, and the notice says `Nothing moved:` and the store's reason. The write names its todo by the id of its store row (`todoIdOf`), so a line written since, or a second press before the list redraws, cannot send it to another todo. | no | e2e `todos/pane/keys.spec.ts`: `#397 a state write the vault refuses leaves the row as it was and says Nothing moved and why`; `todos/pane/order.spec.ts`: `#947 B1 a press the store refuses says so, draws its todo unstruck, and asks the list once`, `#947 I3 a refused press keeps the notice and the row where it was through a redraw` (#397) |
| 125 | `t` on a row whose line a write landing since has shifted, or turned into another todo. | Gone: `t` names its todo by the id of its store row, so no line written since can send it to another todo. | no | None: the ordering no longer exists. |
| 126 | A state key, a card drop or `t` on one of two or more todos of the same line in one note (twins), after a write landing since. | Gone: each twin is a store row with its own id, and a press names the row's id, so it never reaches the other twin. | no | None: the ordering no longer exists. |
| 127 | `<leader>x` (or the palette's cycle) on a todo whose `🆔` stands on another todo line too, in the same note (a pasted copy) or in another. | The press finds the todo's log line and its dependents by id, so two todos carrying one id would share them: setting one done would unblock what waits on either. So it checks the id first. Where another todo line carries the id, the notice says `Nothing moved: 🆔 <id> is on another todo too: <note> line <n>`, with `, and <k> more` where there are several. Session, log and `⛔` lines name the id without carrying it and do not count. `<leader>x` cycles its own line in the buffer, which autosave writes, and its parts and a recurring copy follow it as on any press, but it moves no log line and no dependent, neither as an edit to the buffer (a todo in today's own note, where both would be) nor as a write to another note, and it says the same. The press itself asks the buffer, and the page's listing of `GET /api/todos` for the other notes, since it cannot wait on the vault; the route then asks the buffer before the press for a twin in its own note, not the disk, since autosave can be a quiet period behind, so a copy pasted a moment ago is refused and a twin just changed is not. A todo with no id asks nothing more. The pane's presses, the board's and the phone strip's name a store row, whose id no other row carries, so they check nothing. | no | todo-api-state: `#534 A4 a <leader>x into done whose 🆔 stands on another todo line logs nothing and unblocks nothing`, `#534 B2 a <leader>x on a copy the disk does not hold yet is refused`, `#534 B2 a <leader>x whose twin the buffer no longer holds is not refused` (green on main too, which refused nothing: it guards against refusing off a stale disk); `todo-commands.test.ts`: `#534 A4 B1 a press on a twin carrying the other's 🆔 moves its own line and no log or dependent`, `#534 A4 B3 a press whose 🆔 another note carries moves its own line and no log or dependent` (#534) |
| 128 | Two `<leader>x` (or the palette's cycle) into or out of done, on two todos of one note or on one todo twice, before the first press's log write answers. | Both presses read today's daily note before either writes, so the second's write names a base the first moved past. The log write goes through the same read, change and save that `updateNote` retries on `Changed on disk`: the second press works its `## Done` line out again on the newer text, so both lines land, a then b, and a reopen drops the line the first press wrote. A note holding a stray log line retries the same way. Where today's note did not exist at either press, the second press's create is refused and it writes into the note the first made. A reopen whose listing does not name today's note yet still reads the note the disk holds. Each press's writes beyond the buffer (the twin check, the log and the write back) wait for the press before it to settle, so the lines land a then b and a reopen sees the line it drops, whatever order the answers come in. A press that never answers holds the next back only for a bound, after which the next goes on its own. Three refusals in a row still say `Nothing moved: Changed on disk`. | no | todo-api-done-log: `#538 A1 two <leader>x into done in flight on one note both log, a then b`, `#538 I1 a quick reopen after done drops the line the first press logged`, `#538 I2 a stray log line in another note is dropped on the newer text`, `#538 I3 two presses on the first log of the day both log`, `#538 A2 a log write refused three times still says why`, `#538 I1 a quick reopen whose read comes before the first save still drops the line`, `#538 A1 two presses into done land a then b when the second's reads answer first`, `#538 B1 a reopen before the listing names today's note drops its line` (all red on main), `#538 B1 a reopen with no note today writes nothing and says nothing`, `#538 B2 a press that never answers holds the next one back only so long` (red before the bound); home-route-twin-ids: `#538 A3 two quick <leader>x into done with vim on both log`, `#538 A3 two quick palette cycles into done with vim off in a narrow window both log` (#538) |
| 129 | A `<leader>x` that recomputes dependents, in the buffer or by its write back to other notes, while a `⛔` names a `🆔` that two todo lines carry. | Which twin decides cannot be told, so while one twin is open a dependent naming that id stays as it is, `[ ]` or `[b]`, in the buffer and in every note the write back reaches, unless another of its blockers is open, which blocks it as before. With every twin closed the blocker is closed whichever was meant, and the dependent moves as on any closed blocker (#544). The buffer counts an id as twinned, and leaves the dependent, where a todo in it and a todo in another note carry it, since it cannot see the other's state. The pane's `b` picks a store row, whose id no other row carries, so it checks nothing. | no | todo-write-blocked: `#537 A4 blockedLines leaves a dependent on a twinned 🆔 as it is, %s` (two cases), `#537 I4 a dependent with one twinned blocker and one closed blocker stays as it is`, `#537 B1 a twinned blocker beside an open one still blocks, %s` (two cases), `#544 I1 blockedLines opens a dependent on a twinned 🆔 whose twins are both closed`; `todo-commands.test.ts`: `#544 I3 <leader>x opens a dependent on a twinned 🆔 whose twins in the buffer are closed`, `#537 A5 <leader>x on another blocker leaves a dependent on a twinned 🆔 in the buffer`, `#537 A5 <leader>x leaves a dependent whose blocker another note carries too` (#537) |
| 135 | A `<leader>x` out of done that drops the todo's `- ✅` line, or one into done that checks whether the id is logged already. The pane's presses, the board's and the phone strip's go to the todo store and write no log line. | A `- ✅` line names the id when the id is its last `kt-` word, or its last word where it has none, and the line sits outside a code fence. A log line of another todo whose words mention the id stays, so does a fenced one, and a tick of a todo whose id stands only in such words still gets its line. The share untick reads it the same way (row S4), and `frontend/tests/fixtures/done-lines.json` holds both. | no | todo-write-log: `an untick drops only the line that logs the id (#1301) > keeps a log line of another todo whose words mention the id`, `> keeps a log line inside a code fence`, `> still drops the todo's own line, one with words after its id too`, `> logs a tick whose id stands only in another todo's log words`, `the done lines the server writes too (#726) > dropDone drops what the server drops: %s`, `> doneLineEdits takes out what dropDone does: %s` (red before #1301) |
| 146 | `t`, a state key, a card drop or the phone strip's timer before the page's file listing (`GET /api/files`) has answered; or a `<leader>x` into done then. | A press reads no listing: it is one store write by the todo's id, so one before the listing answers writes as one after it. A `<leader>x` into done whose listing does not name today's daily note yet makes that note for its log line, and where a press just before made it already, writes into it (row 128). | no | todo-api-done-log: `#2061 a press into done before the listing answers logs into today's note on disk`; e2e `todos/presses.spec.ts`: `t before the file listing answers starts a session on the todo (#2061)`, `X before the file listing answers sets the todo done (#2061)`; `panes/narrow/todo-pane.spec.ts`: `timer tapped before the file listing answers starts a session in today's note (#2061)` (#2061) |
| 147 | Two or more `x` presses (or state keys, or the phone's state button) on one row straight after each other, before the list redraws. | Each press draws its state on the row at once and walks the todo's store row by its id, one write at a time (`inTurn`), so the store walks the todo on, open to doing to done, however the note around the todo's embed changes. The list is read once, after the last press settles. | no | e2e `todos/list.spec.ts`: `two x presses straight after each other walk the row on to done (#2080)`; `todos/presses.spec.ts`: `sends every press of x, however fast, and asks nothing`, `of two presses, the list is read once the last lands, not when the first does`; `panes/narrow/todo-pane.spec.ts`: `two presses of a row's state button straight after each other walk it on to done (#2080)` (#2080) |
| 148 | `t`, `@`, `i` (edit), `b` or `m` on a row straight after an `x` on it, before the list redraws. | Each key waits behind the `x` (`inTurn`) and names the todo by the id of its store row, so it reaches the todo the `x` walked. `@` builds the line it sends from the state the store answered the `x` with, not the box the row drew. `b`, `m` and `@` send the version of the row as the `x` answered it, and `i` the version it read; `i` and `@` step past each version a write from this tab made (`sentAt`). So the `x` makes none of them stale, while a change made elsewhere since does: the store refuses it and nothing is written (row 152 for an edit). | no | todo-api-store: `#2084 tags the todo in the state its row has now, not the box the press read`, `#2247 sends the version the edit read, past a press from here but not past a change from elsewhere`; e2e `todos/list.spec.ts`: `t straight after an x starts a session on the todo the x walked (#2084)`; `todos/twin-ids.spec.ts`: `a key straight after an x, before the x's write answers (#2084)` (`@`, `i`, `b`, `m`), `with vim off, a key straight after an x (#2084)`; `panes/narrow/todo-pane.spec.ts`: `timer tapped straight after a state press starts a session on the todo it walked (#2084)` (#2084) |
