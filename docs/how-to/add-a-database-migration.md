# Add a database migration

Alembic owns every table in Postgres: the `finance` schema, the RSVP reading
places, the record of what agent tokens do and the
[pieces index](/explanation/models-on-the-vps/the-pieces-index.md), which is derived from the vault. The dev database must be
running and current before you generate anything, or the autogenerated migration will
try to recreate what is already there.

## Generate

```sh
mise run db:up
mise run db:migrate
mise run db:revision -- -m "add tags table"
```

`db:up` builds the image from `deploy/postgres/Dockerfile` only when the box has
none yet. On a box whose container still runs plain `postgres:17-alpine`, or
after a change to that Dockerfile, run `docker compose up -d --build db` once:
it swaps the container and keeps the `kasten_pgdata` volume, every database in
it included. Without pgvector, migration 0013 fails with `extension "vector" is
not available`.

`db:revision` compares your SQLAlchemy models against the live dev database and
writes the difference to a new file under `backend/alembic/versions/`.

A finance table names its schema in `__table_args__ = {"schema": "finance"}`.
Autogenerate compares only the default schema and `finance`, so a schema kasten
did not make, an extension's for example, is never written into a migration. It never writes `CREATE SCHEMA` either: a new schema is an
`op.execute` by hand, as in `0001_finance_schema.py`.

## Review

Always read the generated file. Autogenerate is good at columns and tables and
bad at everything else: it misses server defaults, it does not see column
renames (it drops one column and adds another, which throws the data away), and
it leaves index changes out more often than you would like. Fix the file by
hand where it is wrong.

## Apply

```sh
mise run db:migrate
```

## Roll back

```sh
mise run db:downgrade
```

That reverses one migration. Check that the `downgrade()` function in your file
actually undoes what `upgrade()` did before you rely on this.

## Start over

If the dev database has drifted somewhere you cannot reason about:

```sh
mise run db:reset
mise run db:migrate
```

This destroys the volume and every row in it. That is safe here, and only here:
the notes live in `vault/`, the dev database's finance rows and agent token
record are test data, and a lost RSVP place only means the next run starts at the
top. Never point this at production, where the finance rows are the only copy
and the reading places and agent token record are real.
