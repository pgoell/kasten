* **Update**: opening a book draws the note's highlights on the page, and `gf` on a highlight block opens the book at that passage. Both run off the quoted words and nothing else: the pane reads the note's blocks, searches the chapter on screen for each quote, and draws what it finds through foliate's overlay, so a highlight deleted by hand stops being drawn on the next save and a quote edited past what the book holds is skipped in silence. The draw pass runs in a `queueMicrotask` rather than in the `create-overlay` handler, because foliate emits that event from inside `#createOverlayer` before `attach` has hung the overlay on the view, and a synchronous read finds the right section with no overlay on it and draws nothing at all. The finder takes every quote at once and walks the document once, building one collapsed string and calling `indexOf` per quote: measured in Chromium against a real 26 section book with two hundred highlights in its biggest chapter, 3.0ms to find them all against 638ms for a walk per quote and 15.9 seconds for foliate's own matcher over the same section. `gf` reads a second thing after the wikilink, a highlight block under the cursor, from any of the four places a cursor can sit in one, and the anchor line is what tells a highlight from a quotation, which is what keeps Enter on a plain blockquote moving the cursor down. The book opens beside the note when nothing has it open and the focus moves to the reader already reading it otherwise, the seek being handed over only when the move was allowed and cleared one render later so a reader opened an hour on replays nothing. A cfi appears twice and neither is a second selector: `gf` builds one from the range it just found and throws it away, and the jump writes the `reading:` bookmark like any other page you turn to. [Reading a highlight back](/reference/highlight-format.md#reading-a-highlight-back) states the block rule, [Wikilinks](/reference/editor-keys.md#wikilinks) carries the key, and [How a highlight is drawn again](/explanation/books-in-the-vault.md#how-a-highlight-is-drawn-again) says why the words are searched for rather than a place stored, with what it costs.
* **Update**: tables line up and take the tab key. `<leader>=` pads every cell in a table to the widest one in its column, squares the row of dashes off to match and obeys what those dashes ask for, `:---` left, `---:` right and `:---:` centred, with three characters the narrowest a column can be drawn and still leave a legal row. Nothing is thrown away on the way: a row carrying more cells than the dashes do grows the table a column rather than being cut back to the head, the walls a row left off its ends are written in, and a `\|` inside a cell stays a pipe. Tab walks the cells left to right and down the rows, stepping over the dashes, which are nobody's cell, and writes an empty row when there is none left to land in; Shift+Tab walks back and declines in the first cell, so the key still lifts a line out everywhere else. Every press lines the table up first, so a cell just typed into is squared before you leave it, and a table already square is a move rather than an edit: no undo step and no write of a file nothing changed. The reading is line by line rather than through the parse tree, so `formatDocument` and the tab keys share one idea of what a table is, and the dashes are what say where one starts, a line of prose being allowed to carry a pipe. On screen a table now takes a line decoration per line and the monospaced face, columns lined up by counting characters only staying lined up where every character is one width, and it is the second block after a fence to keep all of its marks: the walk goes on into the cells and colours them but hides nothing there, since a `[[link]]` four characters narrower than the column it was padded to would pull every wall to its right out of true. There is still no widget drawing a real table. [Tables](/reference/editor-keys.md#tables) carries the keys, and [The three blocks](/explanation/live-preview.md#the-three-blocks) says why the marks stay and what the trade cost.
* **Update**: `<leader>w` downloads whatever the focused pane holds rather than a note alone. An image pane hands over the picture, an exam counts as its note, the pane holding the note's path and the cache its text, and the reader says the key bare, `w` beside its own `q`, that pane carrying no leader at all. The two assets go out by the address that already serves them, `/api/assets/{path}` with a `download` on the anchor: their bytes are on disk and not in the page, and fetching an epub only to wrap it in an object URL would hold the whole book in memory to save a request the browser is about to make anyway. Nothing is saved first for either, nothing here having edited them. The note keeps the blob and the save it always had. * **Update**: the shell container hands you zsh rather than sh, with starship drawing the prompt, Debian's completion and syntax-highlighting plugins loaded and the host's aliases, `ll`, `la`, `l`, the coloured `grep` and `claude-d`. The shared setup is `/etc/zsh/zshrc.kasten` in the image and not a dotfile, because the home is a named volume docker seeds once and a `~/.zshrc` in an image reaches a fresh volume and never an existing one; it is appended to Debian's `/etc/zsh/zshrc` rather than written over it, that file binding Home, End, Delete and the arrows from terminfo, which a browser terminal needs. The entrypoint seeds an empty `~/.zshrc` beside the herdr config it already seeds, both because zsh runs its new-user wizard when the home holds no startup file at all, which over ttyd looks like a shell that will not take a command, and because your own aliases need somewhere in the volume to live. Claude Code and codex moved from `/usr/local` to `/opt/npm`, a prefix owned by the user the shell runs as: `claude update` failed because npm's own tree is root's, and chowning `/usr/local` instead would have handed that user ttyd, herdr, jj and rg. An update still lives only in the container's writable layer, so a deploy returns to the pinned version, which is now 2.1.231. [Constraints the box imposes](/explanation/environments.md#constraints-the-box-imposes) says what is in the image and why the update does not survive.

* **Update**: `dsh`, DeepSeek's harness, is the third agent in the shell container, pinned in `/opt/npm` beside Claude Code and codex. It is a developer preview, so the pin is an rc and will move often, and it is the first thing in that image that has to be compiled: it depends on node-pty, which publishes prebuilds for macOS and Windows only, so linux-x64 builds from source and wants python3 and a compiler the runtime has no other use for. The three npm installs therefore moved into an `agents` stage on the same node base, and the runtime copies `/opt/npm` from it, which costs the image 50MB and keeps a toolchain out of a container that is reachable from a browser. It signs itself in unlike the other two: no browser login, a DeepSeek API key read from the environment or `~/.dsh/.env`, and `~/.dsh` sits in the home volume with `~/.claude` and `~/.codex`, so a key set once outlives a release. What the container gets is the command line, `dsh --profile headless "..."`, which answers one task and exits. Its web UI is not served and would need a subdomain of its own if it ever were: the page is anchored at `/`, offers no base path, and its own `/api` is the address the backend already answers on. [Constraints the box imposes](/explanation/environments.md#constraints-the-box-imposes) says what is in the image, and [Terminal](/reference/editor-keys.md#terminal) says what each agent wants before it runs.
