# 2026-08-18: the agent API

* **Correction**: every vault write now runs behind one lock, so two saves cannot land in each other's change. `vcs.py` bracketed a write in a jj change and serialised nothing: A opened its change, B opened its change, A wrote, A snapshotted, and A's edit was recorded under B's description. Racing yourself was the only way to see it, and a second writer that is not the browser makes it ordinary. New module `change.py` holds `vault_write`, an async context manager over one module-level `asyncio.Lock`, and `vault_change`, which brackets the mutation in a jj change and raises when it is not inside a `vault_write`. Eleven write sites moved onto it, the lock taken before the collision check or the digest comparison rather than merely before `begin_change`, because a check that is not inside the write's own lock is a check another request can invalidate. Two of the eleven had no jj bracket at all: the Anki import, whose precheck of every deck name could be invalidated between the check and the write, and asset publication, which could drop a book beside a note while a move was carrying that pair somewhere else. Both are in `jj log` now, the import as one change for the whole export. `trash.move_to_trash` and `trash.restore` take no lock, because the check that must be atomic with the move lives in the route that calls them. The asset lock covers the `os.link` alone and never the body stream, or one slow upload would serialise every save behind it. `vcs.DESCRIPTION` is gone and `vcs.describe` replaces it, reading a new `vcs.writer` contextvar so a write from outside the browser reads `agent(laptop): {path}` in the log; the prefix is formatted inside `describe` rather than prepended by the caller, because `begin_change` compares the whole description against the one in hand. The cost of that is real and chosen: a switch of writer seals the change in hand even when the note has not moved, so alternating browser and agent edits to one note make more `jj log` entries than they used to. The ceiling is marked in `change.py` and is worth stating here too: this reaches the writes this process makes and no others, so the shell container editing the same bind-mounted vault is still the old bug.
* **Update**: an agent outside the box reaches the vault. `/agent/` is a new prefix carrying five capabilities, list, read, search, save and append, behind a bearer token and nothing else, and it is the one prefix that will not sit behind oauth2-proxy. The token is checked in the backend, which makes that check the entire trust boundary rather than a second layer, and the dependency hangs off the router's constructor so a route added later cannot forget it. Tokens are SHA-256 digests in a JSON file beside the vault, never inside it, where one would enter jj history for good and sit one search away from any agent reading notes; a store that does not exist reads as an empty list, so there is no configuration in which the gate opens. `agent.py` holds the five capabilities and no HTTP, because the MCP tools will call the same functions and one path validator is worth more than two that agree today. The read does not go through `vault.read_note`, which is `read_text` and turns every CRLF into an LF: a translated read would hand back content whose digest is not the `sha` beside it. A save carries the digest of the note the caller read and is refused with the current one when they disagree, the comparison happening inside the same write lock as the write, which closes the direction that matters and leaves the other open: `PUT /api/files` stays unconditional, so the browser can still clobber an agent's edit. Because both writes stamp, the `sha` a write returns is the digest of what landed and never of what was sent, and `index.md` and `log.md` are the two exceptions, taking no block at all. One mebibyte is the cap on what a write may leave on disk, measured after the join and after the stamp, because that is the size above which jj stops tracking a new file. There is no delete, no move and no folder operation, which makes the honest claim "search, read, create and edit"; [The agent boundary](/explanation/the-agent-boundary.md) says why each of the four routes that were cut is a specific hazard rather than an oversight, and [the Agent API](/reference/agent-api.md) states every shape.
* **Update**: the notebook mints its own agent tokens. `/tokens` is a standalone route on the `/review` precedent, its own URL with no pane, no leader key and no entry in the editor keys, because a screen visited a few times a year is a URL you type. It lists what the store holds by name and date, mints one from a name, and revokes one behind a native `window.confirm`. The secret renders exactly once in local state a refresh loses, with a copy button and a prefilled `claude mcp add` line built off `window.location.origin`, so the endpoint needs no configuration anywhere; it never shows an existing secret because only digests are kept, and there is no rename, no scope, no expiry and no usage stats. Three routes back it, `GET`, `POST` and `DELETE /api/tokens`, which sit under `/api/` and therefore inherit oauth2-proxy and carry no authentication of their own. That puts minting inside the internal trust zone, which [The agent boundary](/explanation/the-agent-boundary.md) now says plainly: the shell container reaches those routes over the docker network with no session, and it grants that container nothing, since it already has the vault bind-mounted and every other `/api/` route. `Token` and `Minted` are imported from `tokens.py` rather than redeclared, so one definition reaches the OpenAPI schema and `api-types.ts`. The count line in [the HTTP API](/reference/http-api.md) reads twenty-seven now rather than twenty-four, and says the five `/agent/` routes are documented on their own page.
* **Update**: the five capabilities are MCP tools as well as routes. `POST /agent/mcp` speaks streamable HTTP, stateless and answering in JSON, and the tools are thin wrappers over the same `agent.py` functions the REST routes call, so the two surfaces cannot drift into disagreeing about what an agent may do. A refused write is a tool error carrying the sentence the 409 body carries. Three pieces of the wiring are load-bearing and each has a test: the endpoint answers at exactly `/agent/mcp`, mounted at `/agent` with the SDK's own `/mcp` supplying the rest, because the deeper mount would answer the documented URL with a 307 many clients will not follow on a POST; the session manager is entered by the lifespan in `main.py`, a mounted sub-application running none of its own, and it is single-use, so the endpoint is rebuilt on every entry and a test enters twice to prove it; and the bearer check is an ASGI wrapper rather than a dependency, because a dependency does not reach a mounted app, setting and resetting `vcs.writer` so an MCP write is named in `jj log` rather than logged as a browser edit with the suite still green. `POST` is the whole method set. `DELETE` ends a session this configuration does not have and the SDK already refuses it, but it accepts a `GET` and holds a server-to-client stream open even when stateless, where nothing will ever be written to it, so the wrapper refuses that too: on an endpoint reachable from the internet it is a connection held open for nothing. DNS-rebinding protection stays on with the allowlist from the new `KASTEN_AGENT_HOST`, empty meaning any host, which is what dev on loopback needs; leaving the SDK's default answers 421 to everything arriving through Caddy. The `mcp` dependency is pinned with `==` rather than floored, there being no dependabot here, so a bump is a CI answer rather than a production discovery. [Connect an agent](/how-to/connect-an-agent.md) has the configuration for Claude Code, codex, Claude Desktop through the `mcp-remote` bridge and plain curl, and says why claude.ai on the web cannot connect at all.
* **Update**: the vault is reachable from outside the box. One Caddy block on `kasten.pascalkraus.com` carries `/agent/*` to the backend with no `oauth2_auth` in front of it, which makes the token check in the backend the entire trust boundary rather than a second layer, and a misconfigured Caddy exposes an endpoint answering 401 rather than the vault. A token holder can list, read, search, save and append, over REST or over MCP. It cannot delete, move, rename, import a deck, upload a book, fetch a page, reach the trash or open a terminal, and none of those is one setting away: they are not routes under that prefix at all. `deploy/compose.yaml` mounts `/home/pascal/kasten-data/agent` as a directory and never `tokens.json` itself, because a bind-mounted file is a mount point and `os.replace` over one fails with EBUSY, which would break every mint in production while passing every test there is. `deploy/.env.prod.example` gains `KASTEN_TOKENS_PATH` and `KASTEN_AGENT_HOST`, a path and a hostname, no secret, `kasten-migrate-prod` reading the same file. [Deploy to the VPS](/how-to/deploy-to-the-vps.md) carries the stanza, the three curls that check it and the one answer that is an incident rather than a misconfiguration, and says plainly that no CI here can test any of it because the Caddyfile is in another repository. [Two environments](/explanation/environments.md) no longer says the backend holds no authentication code, which this work makes false: the browser path is still gated entirely in front, and `/agent/` is the one prefix the backend gates itself.
* **Update**: the agent surface describes itself. `GET /agent/openapi.json` hands a token holder an OpenAPI document for this prefix, which is what an agent arriving with a token and a curl had no way to get: `/openapi.json` at the root describes the browser's API and sits behind oauth2-proxy, so no token reaches it, and an agent over MCP reads the same five capabilities off `tools/list` instead. Built with `get_openapi(routes=router.routes)` rather than by filtering the whole application's schema, so it defines the models these routes use and no others. That is the point rather than a tidiness: a token holder cannot reach anything under `/api/`, and a schema handing one the map of those twenty-seven routes would give it away for nothing. Gated like every other route under the prefix, by the dependency on the router's constructor. A test asserts the path set, and a second asserts no path outside `/agent/` and no browser-only model appears; the gate test is written against the router's own refusal rather than the MCP mount's, which answers 401 for an unmatched path and would have made it pass either way.
* **Update**: the two browser products can reach the vault. claude.ai and chatgpt.com have no field for a header, so a token minted at `/tokens` cannot be given to either one, and what both have instead is a Connect button that discovers an authorization server. `agent_oauth.py` is that server: two metadata documents, RFC 9728 under both the bare and the path-inserted spelling because Claude follows one off the `401` header and ChatGPT probes the other, RFC 8414 beside them, a consent page and a token endpoint. Authorization code with PKCE `S256` and nothing else, no refresh token, no registration endpoint, no revocation endpoint, no table and no migration. What it issues is an ordinary row in the same `tokens.json`, named for the product's host, so the gate cannot tell an OAuth grant from a string typed into a terminal, `/tokens` revokes both with one button and a note written from claude.ai reads `agent(claude.ai): index.md` in `jj log`. Where each route sits is load-bearing and Caddy is why: `/.well-known/*` and `/agent/oauth/token` are fetched by a machine with no session and no way to get one, while `/api/oauth/authorize` is opened by your browser and rides the block oauth2-proxy already gates, which is why kasten has no sign-in form of its own. The router is registered above `app.mount("/agent", ...)`, a mount matching by prefix, so below it the token endpoint would resolve to the MCP app and answer 401 to the one caller that cannot have a token yet. Consent is a POST from a same-origin form rather than a GET: oauth2-proxy's cookie is `SameSite=Lax` and rides a top-level navigation, so a link could otherwise mint a code into a stranger's pending connector flow. A refusal at that step renders as a 400 and never as an error redirect, the addresses being matched whole against three hosts, because this host carries a `.pascalkraus.com` session cookie. `KASTEN_AGENT_HOST` gains a second job as the issuer, which a client compares as an exact string, the container running uvicorn with no `--forwarded-allow-ips` so anything built from the request would say `http` where the world sees `https`. The `401` from `POST /agent/mcp` now carries `WWW-Authenticate` naming the metadata document, which reverses what [Agent API](/reference/agent-api.md) said about a refusal naming nothing: the body is still one sentence, the header names one public document holding three fields. The five tools carry `readOnlyHint`, true for the three that read, because ChatGPT asks the user to confirm every call to a tool without it. Claude Code and codex are untouched and still send the header; Claude Code cannot use this flow, having no field for a client id and needing registration on demand and a loopback rule on top, and that is left out on purpose. Nothing connects until the `/.well-known/*` stanza in [Deploy to the VPS](/how-to/deploy-to-the-vps.md) is deployed to the Caddyfile in the other repository, before which those paths answer a sign-in redirect. [Connect an agent](/how-to/connect-an-agent.md) walks both products through it, [The agent boundary](/explanation/the-agent-boundary.md) argues what the second door does and does not widen, and [Configuration](/reference/configuration.md) states the issuer's shape.
* **Update**: a connected model is told what it is looking at. The MCP server passes `instructions`, read off `mcp-instructions.md` beside the guides `guide.py` and `okf.py` read theirs from, because prose in a Python string is prose nobody can read in a diff. It says there is no grep, no regex and no tree, what `list_notes` and `search_notes` really do and that the archive is walked past, that a write hands back the sha a read returned and that frontmatter is written for it, and where the five guide notes sit, `reading-this-vault.md` first because the rule by which a `[[wikilink]]` resolves is not guessable. Two channels carry it, because no one channel reaches every client: claude.ai and Claude Desktop discard the `instructions` field, while Claude Code, codex and ChatGPT read it, and `tools/list` is discarded by nobody. So a sixth tool, `read_guide`, hands the same text back on request, and the copy in the field carries one extra line telling a client that has just read it not to call the tool. That line is never in the tool's own answer: a caller of `read_guide` is by definition one that never saw it. A sixth tool and not a sixth capability, and the distinction is the point of this prefix: it answers with a string compiled into the image, reads no note, and leaves the audit a list of five things. It is annotated `readOnlyHint` with the three that read. Claude Code truncates a server's instructions at 2KiB, mid-word and reporting it only under `--debug`, so the text is 1.3KiB and what a client needs first is in the opening lines. It also carries the one filing rule an agent cannot infer: a note nobody named a place for goes in `00 Inbox/00 Agent/`, a path it was given is the path to use, and there is no delete, move or rename to correct a note written somewhere else. Advisory rather than enforced, which is how this vault's other conventions work: the todo format and the ontology are written down and followed, not held to by code. [Connect an agent](/how-to/connect-an-agent.md) counts the tools a `/mcp` check shows and [Agent API](/reference/agent-api.md) states why the sixth is not a widening.
