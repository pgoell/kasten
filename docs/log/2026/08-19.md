# 2026-08-19

* **Update**: `<leader>E` unfolds the file tree down to the note the focused pane holds and puts the tree's cursor on that row. The panel seeds its open folders once, from the note the page loaded on, so every note reached after that, through the finder, a `[[link]]`, a backlink or a periodic key, left the tree folded where it was with the cursor still on row zero: the one view of the vault as it sits on disk had no way of saying where you were. The key is `<leader>e` plus the jump, shifted the way `H` is shifted `h`, and what it adds is a signal the route raises beside the focus one; the panel answers it by unioning the folders on the way to the open path into the ones already open, so nothing you unfolded by hand folds away, and by taking the cursor to the row it computes off the same flattened list the vim keys walk. It reveals an image as readily as a note, `openPath` being the pane's note or its picture. A pane holding neither, and a note the archive filter has cut out of the listing, leave the cursor where it is rather than move it nowhere. [Editor keys](/reference/editor-keys.md) gained the row and a paragraph in its file tree section saying that the load-time unfolding happens once and this is the way to catch the tree up.
* **Correction**: a leader key that needs shift did nothing in any pane but the editor. The browser sends a keydown for the shift key itself before it sends the letter it was held for, so a pane resolving the sequence by hand saw `" "`, `"Shift"`, `"E"`, found `Shift` in neither `leaderAction` nor `leaderPrefix`, and dropped the sequence one press before the key arrived. That made `<leader>H` to `<leader>L`, the four that swap a pane, unreachable from the tree, the todos, the reader, the exam, the review and the image pane since the day they were written, and no test caught it because the helper that types a leader sequence never fires the modifier's own keydown. The editor was never affected: vim resolves the keys there and `vim.js` carries the same list under the name `ignoredKeys`. `heldModifier` in `key-bindings.ts` is that list, and the six panes guard on it as their first line. The new key is what surfaced it, `<leader>E` being the first shifted key anyone would press from inside the tree.
