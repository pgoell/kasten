# 2026-08-18: the reader

* **Correction**: the app now says `/tokens` exists. The token screen shipped with a URL and nothing else, no key, no link and no row in the tree, on the reasoning that a screen visited a few times a year is a URL you type. That reasoning has a hole `/review` did not expose: `/review` is only the phone's shell around a review that is also a pane behind `<leader>gs`, so the route being unlinked costs nothing, while `/tokens` has no pane and no equivalent and was therefore mentioned nowhere in the running app at all. Finding it meant reading the documentation for an address. The keys panel behind `<leader>?` gains a **Screens you type** group listing both addresses and what they are, read off a new `SCREENS` table in `key-bindings.ts` beside the binding tables the rest of the panel derives from. Still no leader key for either: a key is worth spending on something pressed daily, and what these were missing was a mention rather than a binding. [Editor keys](/reference/editor-keys.md#screens-you-type) states both.
* **Update**: the window can be rearranged rather than only walked. `<leader>H`, `<leader>J`, `<leader>K` and `<leader>L` swap the focused pane with the one in that direction, the shifted half of the four keys that move to it, which is how vim spells the pair, `<C-w>h` going to a window and `<C-w>H` moving one, and how hyprland spells it as well. The two panes trade places and each carries what it holds, so the focus needs no moving: after the swap you are in the same pane, somewhere else on screen. The direction is answered off the boxes on screen, the same question the lowercase four ask and against the same rectangles, so the tree the panes are laid out from is not consulted about which pane is left of which. Two panes of one split keep the editors they hold, cursor and undo history and all, React keying a pane by an id that travels with it; a swap across two splits opens both notes again, there being no way to move a subtree of the page between two parents without the browser taking it down first, so the key writes what is waiting before it moves anything, which no move of the focus has to do: the autosave follows the focused pane's note, a swap leaves that note where it was, and nothing else would flush it. What a rebuilt pane costs is on the reference page, the worst of it being an exam in progress, whose answers live on screen and nowhere else. `<leader>z` draws the focused pane over the rest of the tab, and a second press puts the tab back: tmux's own zoom key. Nothing is closed and nothing is written, the other panes being hidden rather than taken down, so an unwritten line, a terminal's socket and a video's place all survive a zoom. Every key that moves the focus turns it off on the way past, the way `select-pane` does in tmux, and the footer says `zoom` while it is on for the reason it says `archive`: a zoomed tab of four panes is drawn exactly like a tab of one, and without the word the direction keys would read as broken rather than as having nowhere to go. [Editor keys](/reference/editor-keys.md#panes-and-tabs) states all five.
* **Update**: the reader opens a pdf as well as an epub. The sidecar rule is unchanged and the suffix is now one of two, which moves one thing: the client cannot swap `.md` for a suffix it has to guess, so `GET /api/books/{note}` takes the note's path and answers with whatever is beside it and an `X-Book-Path` header naming which, percent-encoded because a header is latin-1 on the wire and a vault holds notes called `Grundzuge`. `.epub` wins where a note has both, being the one that reflows. The two are filed apart and typed apart, an epub landing in `00 Inbox/02 Books/` as a `type: Book` and a pdf in `00 Inbox/02 Documents/` as a `type: Source`, because a pdf is as often a paper, a report or a deck, and filing one under `02 Books` would be a word a machine wrote into a vault somebody else reads; `Source` is the ontology's existing name for something written elsewhere, so nothing was added to it. `<leader>cb` now refuses a suffix the reader does not open rather than forcing `.epub` onto the name, which is what turned a picked `Ulysses.pdf` into `Ulysses.pdf.epub` and then refused it for bytes disagreeing with a name nobody chose. `vault/.gitignore` holds three lines rather than two, and that line matters more than the first: jj tracks any untracked file under a megabyte and a paper is usually under one, so where an epub escaped the history by being fat, a pdf would not have. The delete refusal covers both, a note's move carries both, and `IMAGE_SUFFIXES` subtracts both, without which every pdf in the vault would have been offered as a picture to paste into a note.
* **Correction**: foliate's pdf support did not work in this project at all, in either mode, and nothing said so. Its `pdf.js` names its own vendored worker, stylesheets, character maps and fonts with a URL built out of `import.meta.url` and a variable, which vite rewrites into a glob over a pattern it then refuses: the dev server answers `Invalid glob: "vendor/pdfjs/*"` and dies on the module, and the build resolves every one of those URLs to the string `undefined` and emits no error. A glob could not have answered anyway, two of the five names being directories. So a plugin in `vite.config.ts` replaces that one line with a fixed `/pdfjs/` base and stages the five names into `public/`, where the dev server serves a directory untouched and the build already copies one. `enforce: "pre"`, because `vite:import-glob` is a core plugin and core plugins run ahead of unenforced user ones; the id has its query stripped before it is matched, dev stamping a `?v=` token on a dependency, and `optimizeDeps` excludes `foliate-js` so the optimiser's own esbuild copy does not reach that line first. The staging is not laziness about pointing `/@fs/` at `node_modules`: everything served that way goes through the transform pipeline, which turns a `.css` into a javascript module, and foliate fetches those two stylesheets as text, so the text layer lands unstyled with every span in normal flow at the left edge. The page still draws and every selection takes the wrong words, which is the worst way for it to fail, and a frame test now asserts the layer computes to `position: absolute` for exactly that reason. `nginx.conf` gains a `location /pdfjs/` whose `default_type` is javascript, nginx's own mime.types carrying no row for `.mjs`, without which Chrome refuses the module worker in production and nowhere else.
* **Update**: everything the reader does works on a pdf, and three of the four had to be built. foliate renders one through `fixed-layout.js`, which hands out a page and no overlay, no index and no way to build a page's document, so the pane makes foliate's own `Overlayer` per page and hangs it inside pdf.js's text layer, which sits over the page and shares its coordinate space. It is scaled by the inverse of the transform pdf.js puts on the document, read off the computed style rather than off `devicePixelRatio`, because what has to be undone is whatever foliate did; `none` is guarded, that string being what `getComputedStyle` answers before the first render and what `DOMMatrixReadOnly` throws a `SyntaxError` over. A resize was the surprise: foliate re-renders through its own `ResizeObserver` and pdf.js appends its text layer rather than replacing it, so two spans became four and the page read twice, and every highlight would have anchored to the copy the words had already left, `indexOf` taking the first of the two. The pane keeps only the newest generation, using the `endOfContent` marker foliate appends when a render finishes; the canvas looked like the cheaper marker and is not, two renders overlapping when a resize lands inside one and both replacing the canvas before either appends its text. `gf` takes the other arm too: a pdf's sections carry no document to search, so the seek opens the same bytes a second time through `globalThis.pdfjsLib` and asks each page for its text content, which parses and draws nothing, and bytes pdf.js will not open answer the same "not in the book" an honest miss does. The take's refusal narrowed from every fixed-layout book to a pre-paginated epub alone: foliate scales those frames with a css transform, so no rectangle out of one survives, while a pdf is scaled inside its own document and the rectangles are the page's. One cost is accepted rather than fixed and is written down on [the design page](/explanation/books-in-the-vault.md#what-a-pdf-costs): a passage taken out of a pdf lands one line per line of the pdf, because that is where a pdf breaks its lines and puts no space between them, and joining them would read better and stop the passage being found again. The words are the anchor, so the words win.
