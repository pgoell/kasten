# 2026-08-14: the player, decks, tooling and exams

* **Update**: the foot of the window says what is running. Production reads the release, which the backend takes off its own installed package, and development reads a commit per service, `be d99325a fe d99325a`. The two halves have to come from different places, because neither can answer for the other: the backend reads `.git/HEAD` beside itself on every call and falls back to the release where there is no repo to read, which is exactly what a production image is, while a bundle in a browser has no repo at all, so `vite.config.ts` reads the same file when the dev server starts and stamps the answer in. `.git` is read rather than `git` run, neither image carrying the binary. The asymmetry is the useful part: the backend says what is running now and the bundle says what the tab in front of you was built from, so a tab left open across a rebase shows the two apart rather than behaving strangely. The declaration of the stamped constant lives in `frontend/src/build.d.ts` and not beside the export that reads it, because esbuild refuses to substitute an identifier the file itself declares. The shell is left out: it reports to nobody, and a route of its own would be plumbing for a container you look at rather than through. [HTTP API](/reference/http-api.md) gained `GET /api/version`, and [Which one you are looking at, and what it is running](/explanation/environments.md#which-one-you-are-looking-at-and-what-it-is-running) carries where each half comes from.
* **Update**: a deck is a tag rather than a note, and one card can carry a tag of its own. `#flashcards/aws` in three notes was three rows called `aws`; it is now one deck, one sitting over all three, each rating written back into the note the card is in. Tags at the head of a card's first line are that card's and add a deck rather than replacing the note's, so the one question about dbt in a note about stored procedures is asked in `databases` and in `dbt` both, and a card in a note nobody tagged becomes a card by tagging its line alone. That is the one place the borrowed format is read differently: obsidian-spaced-repetition takes a card's own tags as the whole of its filing and reads a tag on its own line as governing the cards below it, and it still asks every card here, filing that one under `dbt` alone. What a tag means moved into `deck-tag.ts`, because the overview counts off the matched lines and the session parses the notes whole, and the rule had to be one rule rather than two. `breaks` in `srs.ts` now stops on a heading rather than on any hash: `#flashcards/dbt What is a macro?` opens a card written over several lines, and reading its tag as a heading left that card no front to be asked by. The session holds a text per note and a queue of note and ordinal rather than one text and one ordinal, the ordinals surviving a rewrite that inserts a comment line for the same reason they did before. [A card in a second deck](/reference/flashcard-format/writing-cards-and-decks.md#a-card-in-a-second-deck) states the format and [A deck is not a note](/explanation/spaced-repetition.md#a-deck-is-not-a-note) says why it adds rather than replaces.
* **Update**: the pre-commit gate type-checks the frontend. `lint` already ran `ty` over the backend, so TypeScript was the one half of the repo where a type error could reach a branch and wait for CI to say so; `fe:typecheck` is now a third dependency of it. The catch it buys is the shape nothing else sees: an object built member by member against an interface, `editor.tsx` forwarding every `EditorCommands` member into the vim facet, where a missing member is a type error and nothing at runtime until the key is pressed. Biome cannot see it, being a linter rather than a type checker, and a test only sees it if somebody wrote one for that key. The gate goes from a third of a second to two, almost all of it `fe:build`, which `fe:typecheck` drags in to emit the gitignored route tree. CI lost its separate typecheck step in the same breath: `mise run lint` now fails on the same check first, so the step could never have gone red on its own. [Lint, format and types](/reference/mise-tasks.md#lint-format-and-types) says what the gate runs.
* **Update**: the player sits under the note and answers a key pressed in it. `<leader>gv` splits `col` rather than `row`, a book being a column of text that reads beside a column of notes while a player is a 16:9 box wanting the width the note wants too, so the two share the height instead. `<leader>v` then starts and stops it from wherever the cursor is, which is the rhythm the pane was built for: a sentence goes by, you stop it, you write it down, you start it again. The frame carries `enablejsapi=1` and is sent `playVideo` or `pauseVideo` across the origin, so nothing about the key moves the focus and the note never loses the cursor. Which of the two goes is read off the player rather than counted here: the pane subscribes once the frame loads and YouTube streams `playerState` back, so a video paused by a click is still known to be paused and the next press starts it instead of stopping it twice. Buffering counts as running, or a press during it would start the video again rather than stop it. The signal is a counter held by the route and handed to one pane, the pane playing for the note the press came from, the same shape `focusSignal` already had: the key is pressed in one pane and the frame is in another, and a boolean has nothing to say the second time. A press with no player open raises a number nobody is listening to, which is a key that does nothing rather than one that has to check first. [Playing it without leaving the note](/reference/editor-keys/video-pane.md#playing-it-without-leaving-the-note) says what the key does and what it cannot hear.
* **Update**: a note remembers where each of its videos got to. `noteVideos` answers with every YouTube link a note carries rather than the first alone, each one once, so a note about a course holds a lecture per section and `n` and `p` step through them with the header counting `2/5`. The position lives in `watching: {iDulhoQ2pro: 77, TQQlZhbC5ps: 118}`, keyed by the video's own id: reordering the note moves nothing, and two lectures in one note cannot overwrite each other, `setWatched` reading the other entries back out and writing them again. Flow style on one line because `setField` writes a line at a time and a block mapping would be indented lines it reads as belonging to the field above; it is ordinary YAML and `frontmatter.py` reads the same mapping. The write is reported on the edge rather than on the state, a player streaming its state while it plays and a report per delivery being one that never settles, so stopping is the moment worth writing and it happens once. Which route the position takes into the note turns on the focus, and the two are complementary. The focused pane's note is one somebody may be typing in, so the position is edited into the buffer with `addToHistory` off, the autosave carrying it out and `u` never taking a bookmark back; a note anywhere else goes through the reader's own guarded write, whose whole rule is that it refuses the focused pane's note. That write gained a parameter and lost its hardcoded field: the reader passes `setField(text, "reading", cfi)` and the player passes `setWatched`, and the read stays inside the guard because everything in there is about the note not moving under the write. The pane's URL is held rather than derived, a position written back into the note being a note that changed, and a URL recomputed from it would carry a new `start=` and remount the frame mid-watch. [Where you got to](/reference/editor-keys/video-pane.md#where-you-got-to) says what is stored and which route it takes.
* **Update**: a release stopped rebuilding what had not changed. `shell/` had not been touched in eleven commits across three releases and was rebuilt for every one of them, four minutes on the critical path of a five minute deploy, of which two minutes was exporting a build cache and one was reinstalling three npm agents that were already in the image. The workflow now diffs the tag against the release before it, per component and along the paths that component's Dockerfile actually copies, and where nothing has moved it copies the earlier image to this release's tag with `docker buildx imagetools create`: a manifest copy inside the registry, no pull, no build, no cache export. What that hands the deploy is the digest that was already serving under the earlier tag rather than a fresh build of the same sources, which is the stronger guarantee of the two. The backend and the frontend are rebuilt on every release by construction, the version bump landing in `pyproject.toml`, `uv.lock` and `openapi.json`, so the whole of the saving is the shell. Two guards stand in front of it: a first release has nothing to compare against and builds, and a `previous` tag with no image left in the registry builds too, because a deploy pulling a tag that was never pushed is the one failure this could otherwise cause. The checkout takes the whole history now, neither the tag list nor the range existing in a shallow clone. [Cut a release](/how-to/cut-a-release.md#3-tag-and-publish) says what is rebuilt and what is copied.
* **Update**: a scenario matching question is asked, a row at a time. `ccar-p` writes five of them, one instruction over a row of scenarios and one option set they all classify into, and those five were the ones the pane counted as `not askable`: a 58 question sitting of a 63 question note. A row is now read as its own question over the shared options, lettered `A` to `J` in the order the `Options:` line writes them, numbered under the question it came from, `1.11.1` to `1.11.5`, and carrying the instruction over the rows in its stem so it reads on its own in the pane and in a result note. Splitting them in the parser rather than teaching the pane a second kind of question is the whole of the decision: the grading, the section score, the reveal and the result note go on knowing one kind of question, and the change outside `exam.ts` is the pane importing the letters it used to declare. The answer names a row by its position rather than by a letter, `1 → MCP server; 2 → direct API integration`, which is a key line with no `Correct:` in it and therefore a second key pattern beside the first. It goes under the question or in the key at the back, inline winning there as it wins everywhere. An answer names an option by its text rather than pointing at one, so the two are compared with the case, the spacing and a closing full stop taken off, and a row whose text names no option is left unscored rather than marked wrong, which is what an unanswered question already got. What it costs is a sitting that counts rows: `ccar-p` is 83 questions rather than 63 and its first domain is weighted 15 rather than 11. That is the honest count of what you were asked, and it is why a row is scored on its own rather than a matching question being right only when all five of its rows are. [Scenario matching](/reference/exam-format.md#scenario-matching) states the format.
