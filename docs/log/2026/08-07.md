# 2026-08-07

* **Update**: [Panes and tabs](/reference/editor-keys/panes-and-tabs.md#panes-and-tabs) gained `<leader>h`, `<leader>j`, `<leader>k` and `<leader>l`, which move to the pane in that direction and stand still at the edge. The section says why the directions are answered against the panes' boxes rather than against the tree they are laid out from, and gives the case that settles it: four panes in a square are `row[col[A,C], col[B,D]]`, so walking the tree rightward out of C arrives at B, which is the pane diagonally across. `<leader>o` is still there and still wraps, which a direction does not.
* **Update**: [Panes and tabs](/reference/editor-keys/panes-and-tabs.md#panes-and-tabs) says a divided window draws every pane inside a border, blue on the focused one, and that a single pane has none.
* **Update**: [HTTP API](/reference/http-api.md) gained `GET /api/events`, which reports every change to the vault as server-sent events. The section says what an event carries, why there are three kinds and none for a note that is new, why a folder move arrives as a `listing` naming no note at all, why nothing under a dot-directory is ever reported so the vault's own jj repo stays off the stream, and that the note text does not travel: a client that wants it reads the note. It also names the two lines that are not events, the `retry:` field and the comment every 30 seconds.
* **Update**: [HTTP API](/reference/http-api.md) no longer says a note edited by hand or by `git pull` while it is open in the browser is overwritten by the browser, which stopped being true. `PUT` still refuses no write whose base has moved, and the page now separates that from what the browser does with the stream: a note nobody is typing into takes the new text, and one holding unsaved edits stops autosaving and says so. The count at the head reads nine endpoints rather than seven, which it had been since before the folder route landed.
* **Update**: [Saving](/reference/editor-keys/saving.md#saving) says what happens when something outside kasten writes the open note. It is the page's first list of save states: `Changed on disk` stands while the vault holds text the buffer never saw, autosave writes nothing while it stands, and `:w` overwrites the vault and clears it. The section gained `:e` and `:e!` beside `:w`, and says the two of them are the two answers to one question, which writer wins: `:w` keeps your text, `:e!` takes the vault's, and `:e` without the bang declines a buffer holding unsaved text the way vim's does. It names every way to another note that declines while the state stands, the tree, the finder, search, a followed `[[link]]`, the create prompt and every pane and tab key among them, says a rename declines only when it would move the open note or a folder it sits under, and says the status bar flashes every refusal, a declined `:e` among them, so that none of them reads as a broken key. The one route that still overwrites is on the page as a limitation with its reason: a mouse click into another pane, which the browser has already focused by the time the app hears about it. [Panes and tabs](/reference/editor-keys/panes-and-tabs.md#panes-and-tabs) points at the same state, because that is where a reader looks up a key that appears to do nothing.
* **Update**: [deploy/README.md](../../../deploy/README.md) says `/api/events` must not be compressed, and gives the Caddy request matcher that leaves everything else gzipped. Measured against the running Caddy: with a bare `encode gzip` the stream delivers no headers at all, ever, which reads as a healthy open connection rather than as an error, so nothing downstream would have reported it.
* **Creation**: Added [Terminal](/reference/editor-keys/terminal.md#terminal) to Editor keys, now that a pane can hold a shell. The section says what `<leader>cs` opens, what a session name may be, that the tmux session outlives the pane, the tab and the browser, and that closing a pane detaches rather than kills. It says why the prompt lists nothing: ttyd cannot answer a query about running sessions, and `tmux ls` inside any terminal finds a name you have forgotten. It carries the six `Ctrl+Shift` chords and says why they are not leader keys, which is that the leader is the space bar and a shell must receive the space bar. It says the chords are a guess expected to change, names `TERMINAL` and `TERMINAL_CHORD` in `frontend/src/lib/key-bindings.ts` as the one place to change them, and says this table is the one place that does not follow. It also notes that `Ctrl+Shift+H` is Highlight in the editor and that the two contexts never meet.
* **Update**: [Editor keys](/reference/editor-keys.md) gained `<leader>cs` in the leader table. [Panes and tabs](/reference/editor-keys/panes-and-tabs.md#panes-and-tabs) says a pane holds one note or one terminal, and that a tab holding a terminal is named for its tmux session.
* **Update**: [Two environments](/explanation/environments.md) names the one dev service built on the box, the shell container, and says why: there is no reload loop to bind-mount a tree into, so a Dockerfile change has no other way to be tested before a release ships it. The page says both environments reach the shell only through Caddy with `import oauth2_auth` and that neither container publishes a port, which matters more than it used to now that the thing behind the gate is a shell rather than an API.
* **Update**: [mise tasks](/reference/mise-tasks.md) says `dev:up` rebuilds the shell image, and that it is the only task in the file that builds anything.
* **Update**: [deploy/README.md](../../../deploy/README.md) says what a self-hoster has to get right about the shell container: no published port, and a reverse-proxy route carrying the auth gate. It gives the commands that prove both and says what each answer means, because a `101` there is a shell on the internet and nothing else would report it.
* **Update**: [Terminal](/reference/editor-keys/terminal.md#terminal) and [deploy/README.md](../../../deploy/README.md) say the shell container mounts nothing of the host's home. Claude Code and codex are fresh installs signing themselves in inside the container, into a named volume that survives a rebuild, so the first agent started in there asks you to log in once. The vault is the only thing the container shares with the machine.
* **Update**: The shell container runs [herdr](https://herdr.dev) instead of tmux, on the config this VPS already uses, which was itself migrated from its `~/.tmux.conf`. [Terminal](/reference/editor-keys/terminal.md#terminal) says where that config lives and that the prefix is `Ctrl+Space`, and says why the six kasten chords do not collide with it: herdr takes `Ctrl+Space`, `Alt+Shift+H/L` and `Ctrl+H` through `Ctrl+L`, and kasten takes the shifted `Ctrl` variants. `herdr session list` replaces `tmux ls` as the way to find a name you have forgotten.
* **Update**: [Terminal](/reference/editor-keys/terminal.md#terminal) says what happens when you come back to the tab. Every pane used to claim the focus back on its own, so the winner was arbitrary and a terminal pane lost every time: the shell showed nothing focused and dropped every key until you clicked into it. Only the focused pane revives itself now, terminals included.
* **Creation**: Added `GET /api/terminals` to [HTTP API](/reference/http-api.md), which names the herdr sessions a terminal pane could attach to. It is the one endpoint that reads nothing of the vault: it lists a directory the shell container owns, through a read-only mount of that container's volume, so the backend runs no herdr and cannot start, stop or read into a session. The page says why it reports what exists rather than what is running, and that an absent mount answers `[]` rather than failing. The count at the head reads ten endpoints.
* **Update**: [Terminal](/reference/editor-keys/terminal.md#terminal) says the prompt now lists the sessions that already exist, ranked against what has been typed, with Tab folding one in and a click opening it. It still takes a name nothing answers to, which starts a session. The page no longer says the prompt lists nothing.
* **Update**: [Terminal](/reference/editor-keys/terminal.md#terminal) says how to close a session you no longer want: `herdr session stop <name>` then `herdr session delete <name>`, from inside any terminal, because herdr refuses to delete one that is still running. A stopped session that was not deleted is still offered by the prompt, the list being what exists.
* **Update**: [deploy/README.md](../../../deploy/README.md) says why uvicorn is started with `--timeout-graceful-shutdown 1` in all three places that start it. `/api/events` runs until its reader leaves and uvicorn waits for open connections before it stops, so one browser tab holding the stream used to pin the old process open through every reload and every deploy. The page says plainly that a lifespan cannot fix it, because uvicorn runs the shutdown lifespan after that wait rather than before, and that the `Cancel 1 running task(s)` line it now logs is expected.
* **Update**: [Terminal](/reference/editor-keys/terminal.md#terminal) says `Ctrl+Shift+Q` empties the pane rather than removing it, the way `<leader>q` treats a note. It used to go straight to removing the pane, which does nothing at all on the last pane of the last tab, so a window holding one terminal had no way back to an editor and no way to reach any leader key. The page says this is also the way out of that window, there being no chord that splits, and that the herdr session goes on running either way.
* **Update**: The shell container seeds herdr's config into its home volume on first start rather than reading it out of the image. herdr rewrites that file whenever a setting is changed in its UI, and the image copy was root-owned, so every save failed. Saved settings now survive a rebuild, and a change to `shell/herdr.toml` reaches only a fresh volume.
