Where the path was free it stays free, no temp beside it, and the next upload to it succeeds, which holds for a client that hangs up mid-body too; where it was taken, the book already there is untouched and the answer is a `409`. That refusal is the filesystem's rather than a check racing the transfer: the bytes stream into a hidden, uniquely named temp file beside the target and are hard linked into place, so a path is taken by whichever request gets the link. There is no overwrite and no delete, which is what makes the `409` load-bearing rather than cautious. The cap is 100MiB, counted off the bytes as they arrive rather than read off `content-length`, and the client checks the file's size against its own copy of the number before it sends anything, because Cloudflare sits in front of production with a limit near the same place and answers an oversize body with an HTML page rather than JSON. The first four bytes must be a zip's, which is a usability check and not a security one: the shell pane writes into the vault without ever passing this endpoint. One sentence lands at the foot of the window when an upload fails, and the next press of the key clears it.
